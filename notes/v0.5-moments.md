# v0.5: weights given by moments

Working notes for the modified Chebyshev work. The measurements here are what the design
rests on; the user-facing version is `docs/src/moments.md`.

## The question the spike had to answer

The v0.5 plan calls moment-based Chebyshev "the package's best single argument": an algorithm
the literature dismisses as too ill-conditioned to use, which arbitrary precision is supposed
to rescue. That is a claim about numbers, so it was measured before anything was designed
around it (`scratchpad/wheeler_spike.jl`).

Recovering Gauss–Legendre on [0,1] from `mₖ = 1/(k+1)`, worst node error against the rule
built directly:

| n | Float64 | BigFloat, 200 digits |
|---|---|---|
| 4  | 8.243e-14 | 1.085e-198 |
| 8  | 1.386e-08 | 1.885e-193 |
| 12 | 7.104e-04 | 4.591e-188 |
| 16 | β₁₃ ≤ 0   | 1.224e-181 |
| 20 | β₁₃ ≤ 0   | 2.096e-175 |
| 25 | β₁₃ ≤ 0   | 1.854e-168 |
| 30 | β₁₃ ≤ 0   | 3.169e-161 |
| 40 | β₁₃ ≤ 0   | 5.672e-146 |

Two digits lost at n = 4, fifty-four at n = 40: **1.44 decimal digits per point**, linear, and
the same slope in both columns. Float64 has ~16 digits, so it should die at n ≈ 11, and it
does. The conditioning is not defeated, it is outrun — and since the loss is linear in n and
precision is a parameter, outrunning it is cheap.

Note the failure mode. Float64 does not return an inaccurate rule at n = 16; it returns
something that is not a measure, because β₁₃ goes negative. There is no silent wrong answer
to guard against at that end.

## The modified half

Wheeler's algorithm takes moments against any auxiliary family with a known monic recurrence.
The second spike (`scratchpad/wheeler_spike2.jl`) checked that path two ways:

1. Feeding monic shifted Legendre its own modified moments (`m = [1, 0, 0, …]`) returns
   α ≡ 1/2 and Legendre's own β, to 0.000e+00 at n = 5 and n = 20. Exact, not approximate.
2. Gauss rules for `w(x) = log(1/x)` on [0,1] from its modified moments against that family,
   checked against `∫₀¹ xʲ log(1/x) dx = 1/(j+1)²` — an identity the construction never sees:

| n | Float64 | BigFloat, 200 digits |
|---|---|---|
| 4  | 5.2e-16 | 1.1e-200 |
| 16 | 2.8e-15 | 2.9e-200 |
| 50 | 6.3e-15 | 2.1e-199 |
| 80 | 7.9e-15 | 3.6e-199 |

Flat. No degradation with n in either column. With a well-chosen auxiliary family the map is
benign and Float64 is fine to n = 80 and beyond.

**So the honest claim is narrower and better than "precision beats conditioning".** The
modified algorithm with a good auxiliary family is what you should use and always was; it is
not ill-conditioned and never needed rescuing. What precision buys is the case where you
*cannot* choose the family — a measure handed over as raw moments, or one whose modified
moments have no closed form. That case was genuinely closed to fixed-precision libraries, and
it is open here. Both halves belong in the documentation; claiming only the first would
oversell it.

## The trap in the stopping rule

The first implementation stopped when the rule reproduced its own moments,
`Σᵢ wᵢ πₖ(xᵢ) = mₖ` for `k < 2n`. That is the defining property, it is checked against the
input rather than against anything derived from it, and it is the obvious thing to certify.

It is also almost worthless here. The smoke test asked for 40 points at 50 digits from
ordinary moments and got:

```
residual 7.78e-62   guard 10 digits   cond 1.0
max node error vs Gauss–Legendre: 2.56e-6
verified: true   max residual 3.03e-52
```

Both the certificate and the full verification passed, on nodes wrong in the sixth decimal.
There is no contradiction: matching 80 moments to 1e-52 pins the nodes only to 1e-6 when the
inverse map amplifies by 1e46. The residual of the defining equations is not a proxy for the
accuracy of the solution, and in exactly the regime this feature exists to serve, the gap
between them is the whole story.

Uniqueness makes it concrete. An n-point rule exact to degree 2n-1 is unique, so the returned
rule and Gauss–Legendre cannot both be exact. Neither is: the returned rule misses exactness
by 3e-52, and that is enough to be 2.6e-6 away from the unique solution.

The fix is to stop on the quantity the caller actually receives. The rule is computed twice at
working precisions 64 bits apart and the precision doubles until consecutive iterates agree to
the requested accuracy. Each escalation step already computes a rule, so the comparison is
free, and it needs no fitted constant — with the bonus that the ratio of the measured gap to
the rounding unit that produced it is a real condition number, which goes into the
certificate. After the fix, the same request:

```
residual 8.70e-216   guard 164 digits   cond 4.70e55
max node error vs Gauss–Legendre: 1.13e-51
```

cond 4.70e55 against the spike's independently measured 54 digits lost at n = 40. The two
measurements agree, which is the reason to trust either.

The doubling schedule overshoots by one step (it settles at 716 bits where ~460 would do),
costing about 0.3 s at n = 40. Predicting the right precision from the measured slope would
avoid that, and would also be a fitted constant standing where a measurement now stands. Not
worth it.

## Design decisions

- **The auxiliary family is monic, not orthonormal.** Wheeler's recursion and every reference
  tabulate the monic form; the package's `Recurrence` is orthonormal (`b = √β`). Rather than
  mix conventions, `MonicRecurrence` is its own type and `monic(rec)` converts, so
  `jacobi_recurrence` and friends remain reusable as auxiliary families.
- **A moment interval is its own reference.** Modified moments are stated for the interval
  they were integrated over. The generic `reference(::WeightedDomain)` would have moved the
  domain to [-1,1] while keeping the moments, silently pairing them with the wrong interval,
  so `isreference(::MomentInterval) = true` and `reference` is the identity. `reference_nodes`
  in the verifier needed the matching method.
- **Breakdown is treated as low precision, not as bad data.** `βₖ ≤ 0` cannot come from a
  positive measure, but in practice it almost always means the arithmetic ran out rather than
  that the moments are wrong — the spike shows Float64 producing it at n = 16 for Lebesgue
  measure on [0,1]. So it triggers escalation, and only the precision cap reports failure.
- **Verification uses the auxiliary polynomials, not monomials.** π₀ … π_d span P_d, so it is
  the full exactness claim rather than a sample of it, and the exact integrals are the input
  moments. Its weakness in the ill-conditioned case is understood and is why it is not the
  stopping criterion.

## Status

`test/test_moments.jl`, 45 tests. Exit criterion "a documented worked example where
moment-based Chebyshev fails in Float64 and succeeds at 200 digits" is met by the ordinary
moment case, documented in `docs/src/moments.md` with the table above.

Still open for v0.5: Christoffel modification, `mcdis`, singular weights, Cauchy PV and
Hadamard finite-part, oscillatory/Filon, Stroud E_n^r (carried from v0.4), Gauss–Patterson
(carried from v0.3).

One convenience this work wants and does not have: shifting a known recurrence to an
arbitrary interval. Writing monic shifted Legendre by hand, as both the docs and the tests
do, is the kind of thing the package should do for the user.
